## 1. 拆分结论

建议采用 **前置资料与规则确认 + 9 个功能 Task + 1 次集中版本交付**。

核心拆分依据是功能边界、数据所有权和交接接口。点击、暂存、订单结算、吸收连锁、胜负属于同一个原子事务，因此放在同一 Task；Director 的候选和随机决策独立。美术预览、资源生产和最终绑定作为可见功能 Task 内的步骤，不另外制造一组同义任务。

当前目录仅见 Harness 工具及空白游戏/美术规范模板，未见 Unity 工程，Git 尚无初始提交。因此包含工程基础任务，暂不承诺具体工期。现有所有文件均未跟踪，不能顺手把它们全部提交作为项目基线。

本轮实际进行了文档阅读和骨架文本计数核对，没有实现游戏、创建正式 Task、运行游戏 QA 或启动美术生成。

## 2. 已核对的规则与范围

- C 骨架文本确实为 50 盘、183 件、16 种；A–P 数量依次为 9、12、27、12、15、9、12、18、15、18、9、6、6、6、3、6，均可被 3 整除。
- 前 10 盘确实是 C=8、H=7、B=6；开局订单为 C、H，不消费 Director RNG。
- 两个启用订单槽，每单三件；结构容量四槽不等于开放四槽。
- 暂存五格固定位置；放满仍可继续，溢出点击才失败；吸收留下空洞。
- 严格队列供给；物理只负责表现和命中，不得暗改库存、随机流和胜负。
- 当日无限重试；相同输入及边界下确定性，不要求不同操作路径产生相同订单。
- 不增加关卡、经济、广告复活、道具、排行榜、倒计时、自动求解器或断线存档恢复等未列入本版的功能。

### P01：工程基础与模块边界

- 目标：让后续功能有真实工程和清晰运行入口。
- 范围：按确认版本建立 Unity 工程；把纯逻辑、配置读取、表现适配、平台时间和日志出口分开；明确唯一组合入口；接入实际使用的日志/缓存/构建输出目录。
- 交付：工程文件、模块边界、启动入口、平台限制和运行隔离事实。若不存在存档或服务，明确“不使用”，不为隔离而新增产品功能。
- 接口需求：只读配置访问、核心命令入口、表现事件消费入口、时间来源抽象。名称待工程落地，不伪称已存在。
- QA Intent 来源：§4.3、§8.3、§20.3；核心不得依赖物理轨迹修改业务结果。运行隔离来自 AGENTS.md §4，是流程约束。
- 边界：不借工程搭建制作未经确认的正式场景；无可见变化时不需要美术生产。

### P02：C 骨架、目录与权重资产导入

- 目标：把内容来源固定成可校验、可追踪的正式资产。
- 范围：完整 50 盘数据；DailyChallengeConfig；IngredientCatalog 格式及版本池规则；20 行 Difficulty 3 原样导入；源摘要、导入器版本、配置摘要及校验错误。
- 交付：正式配置文件、导入与校验入口、来源清单。食材资源地址格式在这里定，真实美术资源由 P07 接入；缺失资源不得标成完整可玩交付。
- QA Intent：CFG 01–06；§5.2、§13.1–13.2、§16、§20.1–20.2。额外保留种类数、连续唯一盘 ID、负权重/全零行、源哈希、目录不足/重复映射等正文规则，不能只覆盖编号用例。
- 边界：缺原权重时明确未完成；不提交伪造的正式权重，不把两行样例当作完整配置。

### P03：每日身份、Seed 与独立随机流

- 目标：同日期、内容版本和输入条件下有稳定初态。
- 范围：Asia/Shanghai 日期及可信时间/离线来源；SHA256_U64BE；版本化 PCG32；Mapping/Director/Presentation 独立流；16 种全局一一映射；导出和恢复随机初态；保留算法版本选择入口。
- 交付：日期与 Seed 服务、RNG 包装、映射结果、黄金向量定义所需接口、恢复初态入口。
- QA Intent：DET 01、03、04；§5.1、§6、§16.5、§20.3、§25。初始化 100 次的一致性要求留到正式 QA 执行。
- 边界：重试按钮、动画清理和玩家流程归 P08；本任务提供其底层能力。不开额外难度模式。

### P04：核心状态、库存与事件基础

- 目标：每件食材位置唯一，所有模块读取同一逻辑事实。
- 范围：稳定 itemId/plateId/slotId；顶层、物品、盘子及订单状态；Pending/Active/Buffer/Orders/Completed；开局前 10 盘统计；2 活动槽和 2 锁定槽；Progress/TempCount；事件序号、事务号、快照与不变量。
- 交付：只读状态快照接口、库存查询、开局选择、事件 schema、状态哈希契约。不得把可写集合直接交给物理和 UI。
- QA Intent：§5.3、§7、§11–12、§15–17；开局 C/H、并列 kindId、Progress 不含暂存、B4 覆盖 4/5；DIR 01–03。
- 注意：183 分母下 progress 不会恰好等于 0.40，DIR 01 需要可单独观察阶段选择规则的接口，由版本 Designer 定义夹具，不修改用例。
- 边界：建立模型和守恒能力，不在此重复实现 P06 的点击/连锁流程；P05 使用只读候选快照。

### P05：后续订单 Director

- 目标：每次补单有合法库存、有稳定选择顺序、能解释原因。
- 范围：严格/放宽候选；其他订单预留；b/v/interference/d；五类优先匹配；Progress×TempCount 选行；过滤空类别；权重归一化；kindId 稳定排序；类别内等概率选择；六级 fallback。
- 交付：输入快照、输出选单结果/空槽/异常原因的独立决策接口，以及完整决策轨迹；RNG 消费通过明确传入的 Director 流完成。
- QA Intent：DIR 01–09 中与决策有关的规则；§13 全部分类与 fallback、§18.2、§20.2。严格候选存在但成本超范围时，不能提前放宽成重复订单。
- 边界：本任务输出选单决定，不自行移动暂存物品或推进整局；连锁执行归 P06。d 近似不承担可解性证明。

### P06：点击事务与单局闭环

- 目标：把一次接受点击到事务稳定的全部行为实现为一个完整边界。
- 范围：接受/拒绝条件；Reserved 与默认 0.20 秒输入锁；同类订单优先剩余需求较少再 slotId；最小空暂存格；失败不扣原盘；逻辑清盘；slotId 稳定结算；补单与逐索引吸收；65 次连锁上限；供给接口调用；严格胜利及 Aborted。
- 交付：点击命令、事务关闭事件、统计变化、供给适配调用点、赢/输/中止输出。逻辑先提交，动画只消费事件。
- QA Intent：BUF 01–06、DIR 08–10、SUP 03–06；§9–10、§13.8、§14、§17。拒绝点击不变更核心库存；满暂存仍可处理订单；异常完整性问题不能算玩家失败。
- 边界：这是一个原子功能 Task，不能把暂存、吸收、订单补位、胜负派给不同写入者同时改核心。实际物理供给由 P07 接入。

### P07：主玩法场景、顺序供给与正式资产

- 目标：玩家能在场景内识别、点击食材，并看懂两个订单与五格暂存。
- 实现前：取得有来源截图或用户明确批准的替代基准；确认视口、保留/修改区域、主玩法高精度预览及可编辑源；新资产先有可生产概念、规格和有限生成预算。
- 代码范围：盘子 Spawning/Active/Clearing 表现；空间高度采样、冷却与顺序供给；碰撞及射线/触摸命中；事件驱动动画；订单 HUD 与固定五格暂存；场景中的食材目录绑定。
- 美术范围：必要的盘子、食材家族、场景及 UI 资源；最终目录需 16 个互异有效食材条目。先确认必要代表和家族规格，再生产完整所需资源，不默认给每种食材生成多个方案。
- 交付：可玩主场景、正式独立资源和源文件、用途/pivot/碰撞体/尺寸语义、资源 Manifest、Code Builder 最终绑定记录；正式资源不从整屏预览裁切交差。
- QA Intent：SUP 01–02；§8、§9.1、§10、§16.5、§20.3–20.4。清盘逻辑移除立即释放核心容量，视觉动画不能继续占用；空间仍受其他物体阻挡时不得跳过守卫强行供给。
- 边界：所有权分别登记为美术生产路径和代码/场景/导入元数据路径。美术交接后顺序绑定；不靠物理碰撞结果裁决胜负。性能/画质阈值由确认材料或后续决定提供，不自行编造。

### P08：今日挑战入口、暂停、结果与重试

- 目标：形成打开游戏→今日挑战→结果→同局重试/离开的用户闭环。
- 范围：今日日期身份展示；初始化/配置异常出口；暂停与恢复；Won/Failed/Aborted 流程；事实型结果；同 ChallengeId+ContentVersion 重建；清空旧物理对象、动画、统计和事件序号；retryIndex 管理。
- 可见改动：入口、暂停和结果状态各自确认必要预览，复用 P07 已固定主题与控件；只有确需新增资产才增加概念和生产。
- 交付：会话控制器、页面、结果字段映射和重试资源清理；实现中明确跨午夜及后台生命周期的已确认规则。
- QA Intent：DET 04、§4.1、§6.4、§7.1、§18.3、§20.1。结果包括完成与否、时长、玩家/拒绝点击次数、最高暂存、自动吸收、完成订单数、失败原因和重试数；不做星级段位。
- 边界：不默认增加账号体系、云存档、历史榜单或续局。可信时间接口存在不等于需要新建服务端。

### P09：诊断日志、回放与版本兼容入口

- 目标：一局能导出、解释，并在约定输入边界下跨平台重放比较。
- 范围：P04 事件结构的持久化；输入序号/事务边界及 D03 确认的供给信息；最小回放包；Director 完整字段；状态/核心事件哈希；不变量快照；版本、平台、构建号及全部配置摘要；旧版本算法选择；数据事件与异常上传适配出口。
- 交付：导出/读取/重放/比较的真实接口，机器可读诊断文件，以及日志或上报的实际接入状态。上报目的地未提供时列为缺口，不能把本地文件声称为已上传。
- QA Intent：DET 01–05；§15、§17–18、§20.2–20.3、§25。Rejected 保留诊断但不并入已接受输入；改变表现 RNG 消费量不改变核心结果；重试比较按固定契约处理 retryIndex 等字段。
- 边界：开发回放能力，不提前编写或执行整套正式验收脚本。365 日期与策略模拟的入口需要支持，由正式版本 QA 计划确定夹具和断言后 Builder 接成脚本。

## 5. 顺序、并行与所有权

建议的实现顺序：

```text
前置资料/规则确认
  → P01 工程基础
  → P02 正式配置
  → P03 每日与随机 + P04 核心模型（固定共同接口后可并行）
  → P05 Director
  → P06 原子事务闭环
  → P07 主玩法场景
  → P08 入口/结果/重试
  → P09 回放诊断最终接通
  → 用户启动版本交付 → 集中 QA
```

- P07/P08 的参考收集、预览与概念可在核心实现期间推进，前提是自身需求与视觉基准已经确认；正式代码接入等待固定依赖。
- P09 的事件与哈希契约前移到 P04，功能实现可分步准备，最终交接依赖全部相关行为。
- P07 由一个 Code Builder 持有主场景与最终绑定；P08 使用其固定主题及公共控件。共享字体、锚点、主题和组合入口均由 PM 登记协调，不因为分目录就认为画面无冲突。
- 每个正式 Task 使用独立分支/worktree；运行数据隔离未真正适配前，不并行启动会写共享缓存、日志或账号状态的实例。
- 子代理只向 PM 交接；Designer 仅在确需技术调查时调用，正式版本统一负责 QA Plan。不会对每个功能固定调用一次 Designer 或另设测试代理。

建议模块所有权在 P01 后映射到实际路径：P02 内容配置/导入器，P03 Daily/Random，P04 State/Contracts，P05 Director，P06 Simulation，P07 GameplayView/正式美术/主场景，P08 Session/UIFlow，P09 Diagnostics/Replay。以上为职责建议，不是已存在目录，也不是已授予写权限。

## 6. 集中版本交付与 QA 来源映射

版本交付单独建 Version 记录，不把“跑 QA”包装成第十个业务功能 Task。用户启动交付后，PM 选定提交并在独立 release worktree 集成；工具抽取 QA_BACKLOG；只读 Designer 固定 QA Plan；Builder 绑定脚本和 fixture；候选、脚本和授权固定后由普通 Runner 执行，人工项保留真实证据。

| SPEC 来源 | 主要对应 Task | 版本阶段保留的覆盖 |
|---|---|---|
| CFG 01–06 | P02 | 正常内容、缺盘、种类计数破坏、权重缺行/重复/样例错误 |
| DET 01–05 | P03、P06、P08、P09，P07 提供表现边界 | 100 次初始化、两设备回放、表现流隔离、重试、不同路径守恒 |
| BUF 01–06 | P06 | 第五格、满格匹配、溢出不扣盘、空洞、同类订单优先、重复点击 |
| DIR 01–10 | P04–P06 | 阶段边界、B4、d 分类、空类别、重复兜底、尾局、异常与连锁 |
| SUP 01–06 | P06、P07 | 空间阻塞与恢复、顺序供给、严格赢局与错误中止 |
| §19.6 | P02–P06、P09 | 连续 365 个 ChallengeId；合法、随机、压力策略各至少 10,000 局，合计至少 30,000 局 |
| §20.3 | P03、P07、P09 | Windows、Android 和确认后的目标平台黄金回放；帧率及表现随机扰动 |

§20.2 与发布清单提到 10,000 局，但 §19.6 明确是三种策略各至少 10,000 局；方案保留更完整的原文要求，不能缩成总共 10,000 局。

4–7 分钟、6–10 分钟属于体验目标，尚不是自动化通过阈值；超过 15 分钟按 SPEC 提交骨架体量评审，不自动加速或加入道具。模拟覆盖不等于真人设备测试，也不证明每局可解。

Task 的 READY_FOR_RELEASE 只表示实现交接就绪；QA_COMPLETE 也不代表已授权平台发布。当前请求仅为任务方案，不启动本节中的测试或发布流程。

## 7. 正式落地时每个 Task 必须具备的内容

1. 已确认目标、范围与非目标，以及 SPEC 章节/原 QA 编号来源。
2. 独立 QA Intent ID 与可观察预期；不在 Task 中复制一套完整 Release QA Plan。
3. 固定依赖 Task 修订/提交、真实接口、code/art 拥有路径和共享触点安排。
4. 已解决的业务歧义；可见 Task 的参考、预览、必要概念、资源规格和生成预算。
5. 真正采用的运行隔离入口；未知信息明确写未知。
6. 实现交接时记录实际入口、已知问题和未验证项，不能把脚本存在或配置通过当成游戏通过。

本方案建议先收齐权重与工程/视觉材料，并确认影响库存和确定性的接口语义，再按依赖顺序建立正式任务。无需先创建九个未具备开工条件的工作区。
