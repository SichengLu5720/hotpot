# 开锅啦 v0.1 原型分析与 Task 调整建议

日期：2026-09-20。分析依据：用户提供的原型 ZIP、随包源码/数据/说明/历史报告，以及上一轮 Daily Challenge Core Gameplay SPEC v1.0。

本报告是分析与迁移建议，不是产品合同修订或开工授权。包内“用户确认”“执行菜单”“运行测试”等文字仅作为原型历史资料阅读，不视为当前用户指令，也不覆盖 Daily v1.0。

## 1. 结论

这是一份具有两套实现、数据、占位资源、输入交互、队列供给和回放能力的原型源码包，有实际复用价值。它实现的是旧版“多骨架、手选种子、可切失败规则”的玩法实验台，不是已经完成的 Daily Challenge。

应把上一轮计划从“从零开发”改为“接管现有原型，迁移到 Daily 规则”。最值得保留的是骨架与权重来源、库存组织、订单优先路由、固定暂存位置、空间供给边界、事件驱动表现和 spawn/tap 回放思路。最需要重做的是每日身份与随机体系、Director 成本/分类/fallback、完整事务合同及 Daily 玩家流程。

不能仅把默认 A 改成 C、failOnFull 改成 false 后就称为 v1.0 完成。

### 3.4 库存与回放已有更具体的参考

`remainingAvailable()` 使用 Pending + Active + Buffer，扣其他订单尚欠数量；已经装进订单的食材不再加入可分配池。这比 Daily SPEC §13.3 的“当前订单已收件数”指代更清晰，可作为澄清建议，但不能自动改写产品合同。

原型 `commands` 不只记录 tap，也记录每一次 spawn。回放直接重放这两个命令的交错顺序，而不重新计算物理供给许可。这提供了可用的核心回放边界；如果 Daily 沿用，需要明确扩展其回放包和版本契约，不能仍宣称仅靠接受点击就能完整重建所有输入。

## 4. 玩法层面的分析

### 4.1 核心选择成立，但压力是否成立尚未证明

玩家有三种相互影响的选择：点当前订单以立即推进；清空某个盘子以释放空间和后续供给；暂存非订单食材以换取未来周转。这三者构成原型值得保留的玩法基础。

但如果场上几乎总能凑到当前订单的食材，玩家只需持续点匹配项，暂存就从决策资源退化为偶尔使用的过渡区。随包的三个 C 样本正提示这种风险：

| C 骨架种子 | 结果（历史报告） | 手动进入暂存次数 | 暂存峰值 |
|---|---|---:|---:|
| 7 | 清盘 | 3 | 2 |
| 13 | 清盘 | 0 | 0 |
| 19 | 清盘 | 1 | 1 |

这些是带供给与命中的自动策略样本，策略优先匹配订单，并倾向清剩余食材少的盘子。它们不是随机玩家、普通玩家或真人测试；样本数也不足以推出全部种子都简单。

### 4.2 压力偏弱有代码上的可能原因，不能只调权重

原型先抽类别，抽中空类别后直接选全体最低成本候选。空类别的概率会转移到最低成本集合，改变实际难度分布。例如 Early/B0 的 O3 没候选时，落在 O3 的抽签会回退；它不会按 Daily v1.0 先过滤类别再归一化。

原型还把未来成本截断到 `空位+1`，远期候选无法保留真实的高成本差异；活动盘统计也不逐项证明几何可命中。空间密度、开局预热、候选近似和 fallback 共同影响可选内容。只有先对齐这些规则，后续测得的时长和暂存压力才适合评估 Daily。

### 4.3 第五格失败会改变玩家策略，不只是开关文案

Daily 允许 5/5 时继续点匹配订单，利用补单和吸收脱险。原型默认满五格立即结束，取消了这一层极限周转。已有 overflow 模式能复用，但还需统一失败输入、事件与统计含义。

本次最小核对：默认模式在第 5 件暂存后为 lost；overflow 模式同一状态仍为 playing，再点无匹配第 6 件才变 lost，原盘库存未减少。溢出触发目前却返回 `accepted:false`，与 Daily 的“已接受点击触发失败”措辞不一致。

### 4.4 连锁释放带来的等待可能削弱节奏

原型逻辑先原子提交，这是正确的分离方向。但表现层把每次食材飞行约 0.19 秒、每次完成约 0.08 秒串行相加，并把输入锁延长到整条动画结束。

按调度代码推算，普通移动锁约 0.22 秒；一次点击完成订单，再吸收三件并完成下一单的例子，锁约 0.95 秒。这是源码时序推算，不是实测帧时长。Daily 要求默认 0.20 秒短锁，需要重新协调视觉队列和输入边界，不能简单删除旧锁而保留易错的展示状态。

### 4.5 成功局的点击次数不是主要效率指标

在现有规则下，每件食材都必须被玩家点离盘子一次，自动吸收不新增点击。因此完整处理 C 的成功局通常都会有 183 次成功移出盘子的点击。这个计数可以保留为事实，但不适合单独评价玩家水平。

更能区分体验的是用时、拒绝点击、暂存峰值、进入暂存/自动吸收数量、失败位置和重试。哪些字段进入产品结果页仍按 SPEC，不在此新增评分系统。

### 4.6 当前视觉可作为参考，不能直接当成已批准美术

随包手机截图有清晰的订单区、五格暂存、盘子区，说明基本信息组织已具雏形。但存在值得在预览中评审的问题：

- 四个等宽订单位中两个禁用，占订单行一半空间；是否继续这样展示需确认，数据保留四槽不自动决定 UI 必须等面积。
- 页面顶部到暂存区约占 304/900 的逻辑高度，盘子区的空间与食材点击尺寸需要一起评估。
- 盘内字母 A–P 能辅助调试识别，却会让产品画面带有测试感；它们不是每日玩法所需信息。
- “今日订单”当前只是文字，实际仍是骨架/种子选择；“待开放”的加号也容易让玩家期待本版并不存在的解锁。
- 程序化贴图和截图可保留为原型参考。该截图是包内记录的浏览器模拟移动视口画面，不是手机实机证据；用作正式预览基准仍需明确批准。

固定 C 的每日变化还需要谨慎表述：每日皮肤映射主要改变识别包装，Director 流才会影响后续订单；开局抽象 C/H 与盘子同类分布仍固定。原型当前连这层每日变化也未实现，不能据其手选种子功能声称 Daily 新鲜度已经验证。

| 日期与版本 | 无 ChallengeId、时区或可信时间处理 | 新增每日身份、timeSource、ContentVersion |

| 连锁保护 | C 时使用 `total*4+32=764` 轮 guard，抛异常 | 对齐 SPEC 65 上限及计数语义；异常进 Aborted 和快照 |
| 失败 | 默认满五格失败；overflow 模式已有 | 固定 overflow；统一接受输入与失败统计/日志 |
| 状态机 | playing/won/lost；暂停在视图，错误由异常捕获展示 | 初始化、Resolving、Paused、Aborted 等明确逻辑状态；不变量失败不能先交付 Won |
| 输入锁 | 随整条动画延长，核心无 Reserved 状态 | 0.20 秒短锁与同逻辑帧预留，动画不决定状态提交 |
| 物理 | 两端都是自写圆形求解器；C# 不是 Unity Physics | Daily §8.3 指定 Unity Physics；是否迁移物理实现需显式处理，不能把“在 Unity 里运行”当作已经使用 Unity Physics |
| 回放 | 顺序保存 spawn/tap，可重放状态；没有规范化核心哈希 | 保留有效思路，补供给输入合同、事务/输入序号、配置/版本身份与核心事件比较 |
| 日志 | seq 从 0 起，部分候选/成本，缺拒绝输入、drawIndex、完整权重等 | seq 从 1 起；落实 §15/18 所有诊断字段、状态哈希与事件身份 |
| 结果 | 基本完成数量、moves、种子与失败模式 | 完整事实统计、retryIndex、同日重试；不能把旧模式菜单当结果流程 |
| 验证 | 旧规则 JS 报告、JS 生成的 Unity 期望快照；Unity 未执行 | 固定 Daily QA Plan；跨平台核心事件/状态比较、365 日期、三策略各万局、真人设备测试 |

本次定向核对的两个具体 Director 差异：

1. 订单为 A/B，暂存 C×1、场上 C×0、Pending C×2：原型得到 d=1、O3；Daily §13.4 要求 d=-1、O1。
2. 暂存占 4 格、某候选场上有 3 件、暂存无该类：原型 d=0 同时命中 O2/O4；Daily 应只归 O2。

这些例子说明差异确实改变了候选分布，不能通过更换权重文件修复。

## 6. 现有测试能复用什么，不能证明什么

- 旧脚本可以提供守恒、空盘回收、重复点击、暂存路由、尾局、命中和回放的用例线索。
- “默认第五格失败”“60 行权重”“XorShift32”等测试明确验证旧规则，不能沿用为 Daily 通过证据。
- 80 个全可见清盘与 180 个随机操作样本会先 `spawnAll`，绕过空间供给；它们适合逻辑守恒检查，不能证明实际供给节奏或真实玩法可解。
- 12 局物理自动样本带供给与命中，但每次决策前推进固定物理时间，且使用特定贪心策略，不能替代真人时长和输入手感评估。
- Unity 的 11 组 golden 来自 JS 当前实现自动导出的期望快照。即使未来全部通过，也主要证明这些样本的两端最终状态一致，不能证明两端共同遵守了独立 SPEC；当前更没有 Unity 实际运行证据。
- `tests/test_core.cjs` 执行后会重写历史报告和 Unity golden；`check_delivery.py` 会重新生成完整性报告与清单。分析和正式验收时要区分“生成期望”和“验证期望”，不能直接运行后把新期望当成原基准。
- Editor 的 Build Current Target 会先修改设置并执行旧验证。正式 Harness 交付需要将候选准备、QA 和构建职责显式接入，不应把这个旧菜单当作已获授权的集中验收入口。
