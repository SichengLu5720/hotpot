## 01　目标与交付边界

### 1.1 本版要验证什么

验证“有限可见供给 → 选择单件食材 → 完成三件同类订单 → 暂存周转 → 继续供给”的完整循环是否能运行、是否产生可观察的选择，以及出现卡局时能否定位原因。

本版不是找回原开发者的工程。代码是依据现有分析重新编写的可玩实现；原 APK、IL2CPP 二进制、反编译占位类都不是运行依赖。

### 1.2 交付形态

主工程：针对 Unity 2022.3 编写的 C# 工程，包含数据、场景、完整玩法与 UI、生成的占位贴图、校验入口和构建入口。原包引擎并不等于原工程已经恢复；本项目技术栈是此次交付的默认选择。

辅助试玩：无框架依赖的 HTML Canvas 版本，提供可直接保存打开的单文件 HTML，以及分离的 JavaScript/CSS 源文件。它使用同一套内容数据和同一组明确的原型规则，供即时试玩与自动化检查。

**浏览器版已执行测试；Unity 工程在本环境没有编译或进入 Editor 验证。** 两份实现不能在未经 Unity 校验前被称为已经证明等价。

### 1.3 范围之外

不加入冻结、锁、钥匙、隐藏、遮罩、万能食材、传送带、倒计时目标、烹饪时间、火候、顾客耐心、体力、金币、广告、付费、复活、道具和云存档。不提供自动出题器、求解器、商业后台或关卡编辑器。

保留基础目标槽中的两个扩展位置作为禁用展示；不实现解锁。美术为程序化占位表现，不是最终视觉方案，也不是原包贴图。

## 03　对象定义与容量

### 3.1 食材 Token

每件食材有全局唯一 `id`、种类 `kind` 和盘内位置编号 `slot`。种类编号为 0–15，分别对应 A–P。

同一种类可匹配同一个订单，与原鱼种名称和原鱼 ID 无关。A/B/C 骨架中的字母来自各自独立归一化；本版将归一化字母映射到统一的食材字典，只保留同类关系，不声称保留原鱼的跨关语义。

每件食材在逻辑上只能属于以下一个位置：待供给队列、场上盘子、暂存格、当前订单。已经完成的食材从这些位置移除，并计入 `completedByKind`。

### 3.2 盘子 Plate

字段为 `id / capacity / items[]`。`capacity` 是装盘模板的初始件数，范围 1–5，不是允许玩家往盘里回放食材的背包容量。

取走食材后，其他食材保持原 `slot`，不自动挤到数组最前。盘子半径保持初始尺寸；最后一件取走后，整盘从场上回收，其他盘子继续移动。

不能拖拽盘子、搬整盘、交换两盘或把暂存中的食材放回原盘。

### 3.3 订单 Order

固定 4 个位置，索引 0、1 开放，2、3 禁用。开放订单包含一种目标食材、0–3 件已经放入的食材。

三个同类食材完成一单。若同时存在两个同类订单，优先送往已收得更多、也就是剩余需求更少的订单；仍然相同时按槽位序号升序。

尾局没有足够未预留的同类食材时，开放槽可显示“已出齐”，不制造不可能完成的订单。

### 3.4 暂存 Buffer

固定 5 格，每格最多一件食材。没有匹配订单时，食材进入从左向右第一个空格。

匹配新订单的暂存食材自动离开原格，保留其他食材的格位，不自动压缩重排。玩家不能主动移动暂存格内食材；暂存的功能是等待新订单自动吸收。

## 04　完整流程与状态机

```text
载入数据 / 校验总量
    ↓
按前 10 盘内容初始化两个订单
    ↓
运行中：按队列向桌面供给盘子
    ↓
玩家命中单件食材
    ├─ 可接收的同类订单 → 放入订单
    └─ 无匹配订单       → 放入第一个空暂存格
    ↓
结算：完成满单 → 选新单 → 自动吸收暂存 → 再检查满单
    ↓
判定胜负 / 继续
```

逻辑状态只有 `playing / won / lost`。暂停是视图层状态，不是新的玩法机制；暂停时停止物理、动画时钟和玩家输入。

### 4.1 原子结算与动画

一次有效点击在逻辑层原子完成：移除原位置 → 放到目的地 → 处理完整连锁结算 → 检查终局。守恒统计中没有逻辑“运输中”容器，飞行动画只是事件的可视化副本。

视图按 `move → complete → target → buffer move` 的事件顺序演示变化。播放该次事务的动画期间不接受新的食材点击，避免多指或快速点击重复提交。不是把每个动画帧作为逻辑来源。

单次普通移动约 0.19 秒；订单完成事件增加约 0.08 秒。暂存连锁会延长这一小段输入锁。网页尊重系统减少动态效果设置，减少移动时长。

这是本版降低竞态风险的工程约定，不是原包动画/并发方案的复刻。后续需要连续快速点击时，应扩展为“预留 + 运输 + 到达结算”，不能直接移除输入锁而不改数据模型。

### 4.2 胜利

仅当 `completed == total` 时胜利；同时校验待供给、场上、暂存和未完成订单里都不存在残留食材。

本版计数 UI 标为“已出锅”，显示已经完成整单的食材数量，所以通常按 3 增长。它不是对原截图 `3/99` 计数口径的宣称。

### 4.3 失败

默认 `failOnFull = true`：完整自动结算结束后，五格仍全部被占用，则失败。第五件不是因为“不能放入”被拒绝，而是先进入第五格，再在结算后结束本局。

对比模式 `failOnFull = false`：五格占满仍可继续点击匹配订单的食材；下一次点击无匹配订单、且需要暂存却没有空位的食材时失败。该次失败尝试不把原食材从盘里移走。

两种模式都不在运输表现尚未结束时提前弹出终局界面。没有时间失败、没有平台广告失败规则，也没有自动判定“无解”后擅自刷新内容。

## 05　玩家接触与空间供给

### 5.1 有限供给，不是全部铺开

所有盘子在关卡开始时只存在于逻辑队列。只有通过空间门槛的盘子进入 `active` 并可被点击。

每次生成至多一盘，读取 `pending[0]`，不改变原始模板顺序。生成点按 `[86, 334, 210]` 轮换，加入最多约 ±5 虚拟像素的水平偏移；偏移可能导致碰撞时则不采用偏移。

出现以下任一情况，暂停供给：场上存在中心位置高于生成高度线的盘子；下一生成点会与现有盘子直接重叠。后者是本版新增的插入安全检查，用来避免把新物体强行塞入已有堆积。

**没有固定“场上最多 N 盘”的规则。** 截图中的盘数不是上限。盘子尺寸、堆积形态和剩余内容决定实际供给数量。

### 5.2 本版坐标参数

逻辑坐标原点位于画面左上角，向右/向下为正。虚拟画布 420×900，按屏幕等比例缩放，不拉伸食材和盘子。

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `width / height` | 420 / 900 | 虚拟画布 |
| `playTop / playBottom` | 304 / 828 | 盘子活动区域上下边界 |
| `spawnGate` | 377 | 盘子中心坐标小于此值时暂停供给 |
| 左右边距 | 12 | 不让盘子离开桌面 |
| 1–5 件盘半径 | 33 / 40 / 46 / 52 / 57 | 按初始食材数决定 |
| `gravity` | 960 | 向下加速度，虚拟像素/秒² |
| `spawnInterval` | 0.20 秒 | 最短尝试生成间隔，不保证每次生成 |
| 物理步长 | 1/120 秒 | 固定步长 |
| 接触求解 | 每步 9 轮 | 圆与圆的分离、法向冲量、少量摩擦 |

开局先执行 4 秒等效固定步长预热，仍然经过同样的供给门槛，不直接把一批盘子瞬移到任意位置。玩家进入画面即可看到已经堆积的内容。

本版是自定义圆形堆积，不是原版 Rigidbody2D 参数，也不是完整 Box2D。食材依附于盘内局部位置，不单独参与刚体碰撞。盘子目前不旋转，不改变食材朝向。

### 5.3 点击命中

触屏或鼠标坐标必须转换成虚拟画布坐标。只检查桌面范围内的食材。按绘制顺序逆序检查，优先命中最上层盘子内的食材，不允许穿过前景盘子点击背后物品。

点击盘缘、盘内空白、UI 下方或已经取走的食材都不产生移动。盘内不规定 A→B→C 的点击顺序，盘间也不规定必须先清编号较小的盘子。

原版“已生成”和“纳入可用供给统计”还可能受额外高度阈值影响。本版目标评分把已经生成的食材作为当前供给近似，不对每一种食材逐像素求可接触性；这是明确的近似点。

## 06　开局目标算法

### 6.1 规则

统计队列前 `min(10, pending.Count)` 盘里的每种食材数量；扣除其他已经设置的目标尚欠数量；优先排除已有目标种类；在剩余候选中选择数量最多的种类。

前缀没有候选时改为查看全队列。作为本版安全约束，候选还必须在整个剩余库存中拥有至少 3 件未被其他订单预留的食材。

并列时按抽象食材 ID 升序选择。本版不模拟原生 Dictionary 枚举顺序，也不在开局并列时掷随机数。

### 6.2 回归基准

| 骨架 | 初始目标 ID | 当前食材表现 |
|---|---|---|
| A | A、F | 肥牛卷、豆腐 |
| B | A、G | 肥牛卷、藕片 |
| C | C、H | 香菇、鱼丸 |
| 练习 P | A、B | 肥牛卷、虾仁 |

A/B/C 结果基于去机制且不交换原逐盘顺序的样本。它们不是对原版某台设备、某次随机鱼种重映射后画面的预言。

## 07　后续目标算法：已知结构 + 明确替代成本

### 7.1 触发点与库存预留

只有订单完成时，才为该槽选择新目标。不是两个目标一起刷新，不是关卡开始生成一条固定目标颜色序列。

统计全部剩余的待供给、场上和暂存食材。扣除其他订单尚欠的同类数量后，至少还有三件的种类才是候选。已经放入订单的食材不再作为新目标库存。

候选中存在与现有订单不同的种类时，优先使用不同种类；没有不同种类才允许重复。没有任何可用三件组时，该槽为空，不强行发一单。

### 7.2 查权重表

进度采用 `(已完成食材数 + 当前订单已放入件数) / 全关食材总数`。暂存占用档位为 `min(4, 已占暂存格数)`。

按骨架难度 1/2/3、进度所在阈值（0.4、0.65、0.85、1.0）和暂存档位（0–4）查询 `difficultyRows`，共 60 行。取第一个不小于当前进度的阈值。

例如难度 1、进度不超过 40%：暂存 0 格时为 `[0, .7, .3, 0, 0]`；暂存 4 格及以上时为 `[.9, .1, 0, 0, 0]`。这是类别抽样权重，不是最终“救场概率”。

### 7.3 本版成本 `d`

**以下是新写的近似算法，不能叫“完整还原的原版成本”。**

对一种候选食材，先用暂存、再用场上食材扣除其他订单的预留需求，得到 `usableBuffer` 和 `usableActive`。

如果两者合计至少三件，定义 `d = -min(3, usableBuffer)`。因此场上可凑齐但不用暂存时为 0；可以使用暂存时为负。

如果当前供给不足三件，扫描待供给队列，找到补足目标所需件数的最短前缀，统计其中的其他种类食材数量 `foreign`。定义：

```text
d = max(1, min(空暂存格数 + 1, foreign))
```

该值仅用于区分候选，不是准确的最少操作数、空间阻挡成本或死局概率。截断是本版为了映射五类的明确约定。

### 7.4 类别、抽样与回退

令 `N` 为当前空暂存格数，沿用已观察到的五个筛选条件：

| 类别 | 条件 |
|---|---|
| Order1 | `d < 0` |
| Order2 | `d == 0` |
| Order3 | `1 <= d < N - 1` |
| Order4 | `d == N - 1` |
| Order5 | `d == N` 或 `d == N + 1` |

先按权重抽取类别，在该类候选中按种类 ID 排序，再均匀随机选一个。没有对应候选时，回退到全体候选中的最小成本集合，再随机选择。

空位很少时类别条件可能重叠，本版按每个条件单独判断，不擅自把原来的谓词改成互斥区间。

本版没有实现原方法所有优先覆盖、广告参数、特殊目标和旧版本分支。它只实现一套可解释、可记录、可替换的普通补单策略。

### 7.5 随机性

目标选择使用 XorShift32。空间偏移使用另一条独立随机流，种子由主种子异或常量派生，避免物理更新次数改变目标抽样序列。

相同数据、规则、种子和逻辑命令序列应产生相同逻辑结果。物理浮点和渲染不承诺跨浏览器、C#、平台逐位一致。Unity 与网页逻辑回放的一致性需要在本机执行随包的 golden 校验，不能以 JavaScript 测试替代 C# 验收。

## 09　界面与表现

目标为竖屏；桌面以竖屏画框居中，网页可带独立控制侧栏。手机需要保证订单、暂存和盘子区都在可用高度内。

上方：游戏名称、当前骨架、暂停入口，下一行展示四个目标位置。两个开放目标显示食材图标、名称及 0/3 指示；两个扩展位置显示禁用加号。

中间：左侧“已出锅”计数，右侧五个暂存格。暂存接近满时计数使用警示色，但不自动改变游戏规则。

下方：盘子活动区与简短操作提示。没有底部道具栏，因为本版不实现这些机制。

食材使用不同形状，而不只用颜色区分；盘中食材附小字母标签以辅助对照。表现层可被替换，不应把识别种类的依据改为纹理文件名。

暂停菜单包括继续、切换骨架、修改种子、重开、查看失败时点、导出日志。网页支持键盘操作和触摸，Unity 使用传统鼠标/触摸输入与即时 GUI；没有依赖 UGUI/TMP Prefab 链。

不附带字体文件；网页使用系统字体，Unity尝试使用操作系统已有中文字体并回退默认字体。Unity WebGL 或缺少中文系统字体的设备可能需要后续配置已获授权的字体；本次未做这些平台的显示验收。

## 10　工程结构与职责

```text
配置层 / shared
  game-data.json          唯一可编辑公共数据源
  reference/              三个原始分析样本与难度表
```

## 11　日志、守恒与复现

每次事件包含单调递增序号。记录开始配置、供给、移动、盘子清空、订单完成、新目标、胜利/失败；目标事件包含原因、请求类别、实际成本、候选列表、进度阈值和暂存档位。

逻辑命令只包含 `spawn` 和 `tap(id)`，可以重放逻辑状态。日志不是逐帧录屏，也没有完整保存每次物理时间步；网页导出附最终物理位置，仅用于检查，不承诺重放相同空间路径。

每次有效动作后校验：

```text
对每一种食材：
初始件数 = 待供给件数 + 场上件数 + 暂存件数 + 未完成订单件数 + 已完成件数
```

还检查活跃 Token ID 不重复、订单不混种、不超三件、锁定槽不接收内容、订单未满足需求不超过实际剩余库存，以及胜利时没有残留。

日志含种子、内容版本、规则和操作，不含账号、设备身份、邮箱或联网遥测。本版没有发送日志的远程地址，导出由玩家主动触发。

## 13　待确认的产品决定

**失败时点。** 默认第五格结算后失败，是否改成下一次溢出尝试时失败，需要试玩决定；不应再用静态截图推断。

**目标策略精度。** 本版先使用已知权重结构和明确近似成本；后续是继续定点恢复原分支，还是独立调优，应根据卡局日志和试玩反馈决定。

**空间与节奏。** 盘子半径、供给高度、接触摩擦和输入动画锁都属于本版可调体验，不是原版已恢复参数。

**最终视觉与技术交付。** 当前火锅食材/点单锅/盘子是占位表现；Unity 为默认工程，网页为即时试玩辅助。没有将占位美术当成用户确认的最终高精度预览。
